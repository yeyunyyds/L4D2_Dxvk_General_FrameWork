LDB RT Performance v32 — 纯GPU蒙皮稳定性隔离

本版继续暂停五分钟Beta，只验证GPU骨骼计算、持久网格复用和Host供给成本，不做完整画面验收。

测试步骤（一次F9）
1. 解压到新文件夹，运行 run-performance.cmd。程序会备份并安装配套的client、Host和实验Remix运行时，然后启动游戏。
2. 进入高压测试地图，让人物和普通感染者保持在视野内。回到游戏后按一次F9。
3. 保持同一个场景，正常小幅转头或移动；不要再次按F9。程序自动测试四档GPU蒙皮上限：16、32、64、128，每档30帧，共120帧。
4. 控制台要求退出时正常退出游戏，保持窗口开启，上传最终一个 rt-performance-*.zip。

v31结论
- 4路阶段完整完成60帧，约3.75 FPS；240次GPU蒙皮提交只创建6个持久网格并复用234次。
- 切换到64路后约6帧，Remix记录 VK_ERROR_DEVICE_LOST。Bridge随后等待失效Host满60秒，因此游戏窗口无响应、画面冻结但声音继续。
- 丢失设备前已经累计创建约3.94万个模型网格、销毁约3.81万个；单帧新增几何一度约96 MiB。大量不适合GPU路径或超过上限的模型仍在逐Draw生成CPU姿态网格，导致性能测试没有真正隔离GPU蒙皮。

v32策略
- 性能模式只向实验RT场景提交已审计的 Skin3／Neko3 持久GPU蒙皮网格。
- 不适合GPU蒙皮、包含形变或超过本档上限的模型不再创建CPU姿态网格；达到当帧上限后也不再读取剩余模型几何。它们在本次RT画面中可能缺失，这是隔离测试的预期现象。
- 每个阶段强制校验“全部显式模型提交均为GPU蒙皮”，并记录唯一网格、同帧重复使用、创建／复用、Host耗时、帧率和GPU 3D Engine数据。
- Remix运行时保留原有几何上传→GPU蒙皮→BLAS顺序；只修正蒙皮命令计数在真实提交后未清零的问题，避免后续重复刷新空命令列表。
- 通过标准是完成120帧、恢复成功、没有 VK_ERROR_DEVICE_LOST，且没有CPU姿态网格混入。之后才逐类扩大GPU覆盖并以24 FPS作为下一阶段最低目标。

窗口化或全屏均可，测试过程中不要切换显示模式。不改物理组件，不新增Source线程设置。restore.cmd按安装收据恢复并保留备份。
