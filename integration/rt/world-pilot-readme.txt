LDB RT Performance v34 — GPU蒙皮供给优化

本版继续暂停五分钟Beta，只验证GPU骨骼计算、持久网格复用和Host供给成本，不做完整画面验收。

测试步骤（一次F9）
1. 解压到新文件夹，运行 run-performance.cmd。程序会备份并安装配套的client、Host和实验Remix运行时，然后启动游戏。
2. 进入高压测试地图，让人物和普通感染者保持在视野内。回到游戏后按一次F9。
3. 保持同一个场景，正常小幅转头或移动；不要再次按F9。程序自动测试四档GPU蒙皮上限：16、32、48、64，每档30帧，共120帧。
4. 控制台要求退出时正常退出游戏，保持窗口开启，上传最终一个 rt-performance-*.zip。

v33结论
- 16、32、48、64四档全部完成，共120帧、4,800次GPU蒙皮提交，没有 VK_ERROR_DEVICE_LOST。
- 每档最后一帧的唯一姿态Mesh数都等于提交数，同帧重复为0；v33姿态槽修正生效。
- 64路约13.54 FPS，Host GPU 3D Engine采样平均50.69%、最高52.02%。GPU负载已随蒙皮数量上升。
- 64路每帧Host模型处理约15.96 ms，其中重复SHA-256约6.30 ms，是本版直接优化的CPU供给成本。

v34策略
- 性能模式只向实验RT场景提交已审计的 Skin3／Neko3 持久GPU蒙皮网格。
- 不适合GPU蒙皮、包含形变或超过本档上限的模型不再创建CPU姿态网格；达到当帧上限后也不再读取剩余模型几何。它们在本次RT画面中可能缺失，这是隔离测试的预期现象。
- 同一基础网格在一帧内出现多个姿态时，每个姿态槽使用独立且跨帧复用的Mesh句柄，防止多个角色覆盖同一蒙皮输出缓冲。
- 网格身份仍使用完整SHA-256；每个准备线程复用CNG哈希句柄，避免每次Draw重复创建、销毁哈希对象。不引入可变几何缓存。
- 保留已验证的“主几何命令先提交、专用蒙皮命令随后提交”帧同步顺序，以及v32的真实刷新后计数清零修正。
- 每个阶段强制校验“全部显式模型提交均为GPU蒙皮”，并记录唯一姿态槽、创建／复用、Host耗时、帧率和GPU 3D Engine数据。
- 通过标准是完成120帧、恢复成功、无设备丢失和CPU姿态网格混入，并确认哈希耗时下降。仍以24 FPS作为进入Beta前的最低目标。

窗口化或全屏均可，测试过程中不要切换显示模式。不改物理组件，不新增Source线程设置。restore.cmd按安装收据恢复并保留备份。
