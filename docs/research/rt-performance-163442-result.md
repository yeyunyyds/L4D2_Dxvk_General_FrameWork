# RT Performance v32 163442 结果与 v33 姿态隔离

上传包匹配v32提交`23e1e4c45f8f5c9313cef344e5ba3a4f62101fbe`。性能预览完成62帧后，Remix在16:47:46.884记录`VK_ERROR_DEVICE_LOST`，Bridge随即得到`api_mesh_fence_failed`。完整完成的16路和32路各30帧；进入64路后只完成2帧，128路没有开始，因此本轮未通过。

v32的CPU隔离确实生效。前60帧共1,440次GPU蒙皮提交，只创建17个API网格并复用1,423次；相比v31在60帧内累计创建约3.94万个网格，逐姿态CPU网格创建风暴已经消失。16路阶段为8.39 FPS，但含一次1,438 ms的Present首用停顿；32路阶段为13.71 FPS，Present总耗时仅3.39 ms，采样到GPU 3D Engine平均39.30%、最高44.95%。仍未达到24 FPS，但已证明CPU姿态网格抖动不是当前设备丢失的必要条件。

新的结构问题是同时存在的姿态共享同一个可变蒙皮Mesh。16路最后一帧只有10个基础网格身份，另有6次同帧重复；32路仍只有10个基础网格身份，另有22次重复。Remix会把GPU蒙皮结果写入Mesh对应的可变顶点缓冲，并据此更新BLAS。同帧用不同骨骼矩阵重复提交同一Mesh会产生输出别名和内部BLAS分裂风险；64路负载刚开始即丢失设备与此风险一致，但本轮日志不能单独证明驱动内部的精确故障指令。

v33为同一基础网格在单帧中的每个姿态序号建立独立Mesh句柄，并按稳定绘制顺序跨帧复用该槽位，避免并发姿态覆盖同一输出缓冲。Remix保留已验证的主几何命令先提交、专用蒙皮命令随后提交的帧同步顺序。一次F9仍为120帧，按16、32、48、64各30帧递增；分析器要求每帧重复姿态Mesh数为0。Gameplay Beta继续暂停，先验收无设备丢失、完整恢复及至少24 FPS的下一阶段门槛。
