# 现有模型输入 GPU 重放与材质覆盖

v15 的 105 份配对输入通过 CPU 原 VS、上传字节和绑定核验，但六组模型画面仍损坏。不能将成功的公开 D3D9 查询当作 GPU 几何、实例或 BLAS 已正确消费的证明。本轮增加独立 x64 程序，直接读取用户已有 v15 结果，不向游戏注入、不改变 Source 线程设置，也不重新收集游戏数据。

只读选择本地结果 ZIP 或已解压文件夹，核验 frame 240、420 的重建顶点/索引摘要、Draw 范围、有限数值、相机一致性与上传/绑定记录；归一化列表/条带为三角形列表。固定相机和姿势，去掉游戏、Bridge、原始像素 shader 和动态动画的干扰。原始 7z 需先使用用户已有解压工具解压。模型数据只在本地使用，不随软件发行。

每组执行六个独立进程：RT 关闭的光栅基线；Legacy D3D9 路径分别立即释放缓冲、Present 后释放、持续持有；Remix Mesh API 保留原 UV，以及仅修复退化三角形 UV。共 12 组。两个 API 路径都展开三角形并生成平面法线，顶点位置和世界变换保持不变；与 Legacy 的差异也包含法线/顶点布局，因而改善只能缩小范围，不能直接认定某一缓存或资源寿命就是根因。

材质覆盖同步推进至直接 API 层：中性漫反射基线以外，增加粗糙表面、金属、alpha 裁切、alpha 透明、叠加发光、独立发光和薄玻璃七组。裁切使用程序生成 DDS 棋盘透明纹理；其余使用明确常量。alpha/混合枚举与固定后端 `surface_shared.h` 一致（ALWAYS=7、GREATER=4、Alpha=0、Emissive=6）。这部分验证成熟后端的真实材质入口，**尚未等同于 L4D2 原材质的自动提取、Toon 还原或实时游戏覆盖**。

19 组自动完成，每组 64 Present，保存两张最终颜色与 RT 组深度、法线。所有渲染输出仍须实机人工对照，程序仅报告执行状态，不输出图像验收通过。去除原贴图、关闭剔除、采用诊断照明，是定位几何问题的控制条件。玻璃/透明在黑背景下可能不可见，不能据此判断已成功。位置原样保留，退化 UV 修复明确标记为诊断控制。

一次入口 `run-replay.cmd`；可把已有结果 ZIP 拖到入口上，也可启动后拖入窗口。优先复用同级旧包经完整 SHA256 核验的 runtime，缺失时下载固定依赖。每个进程有单独工作目录和日志，180 秒超时、整套 20 分钟预算；保留清理前状态以区分退出故障与图像失败。结果不重复携带模型输入，按预先计算的压缩大小自动合并到 28 MiB 预算内的 ZIP，尽量只生成一份；超限才拆成独立分卷，供一次性上传。

开发门禁分开记录：Python 损坏输入/归档/分包检查；便携 C++ 二进制边界、三角形法线与 UV 检查；Windows x64 生产上传函数的真实系统 NULLREF 读回/绑定/清理；标准 D3D9 的 API 负例；固定 runtime 的 0.6.4 初始化正例；自带 Python 的隔离入口和包成员摘要。无 B580 的构建环境不提供 Vulkan RT 图像验收或性能结论。

实机结果决定下一步接回游戏的方式：若持续持有显著优于短寿命，修正缓冲交接；若直接 Mesh API 正常而 Legacy 异常，优先复用直接接口；若只有退化 UV 修复有效，继续检验切线生成；若全部异常，保留光栅对照并继续定位相机/后端输入。已验证的材质常量与透明规则再接入实时材质转换，避免同时扩展一批未知行为。
