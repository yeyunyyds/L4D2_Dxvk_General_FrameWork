# 项目重新评估：以 60 源帧到 120 显示帧为目标

评估日期：2026-10-14（用户时区 America/Los_Angeles）。本次只做源码、既有实机数据和公开文档复核，不继续制作测试包。

## 结论与建议

若近期目标是在 B580 上得到可用的 60→120，而非必须交付自有的引擎内置插帧，优先验证现成外部画面插帧产品是否满足需求。若目标场景仍能达到用户此前报告的原生 350～400 FPS，先选原生 120/144 FPS，通常更适合对响应敏感的 L4D2。

内置 FSR 仍有研究价值，但当前架构不宜继续靠掩码与阈值小补丁向可玩版本推进。应先隔离 SDK 的正确性和成本，证明游戏输入，再做精简呈现架构。光追另列目标，不作为插帧的前置依赖，也不把整套 RTX/Remix 移植当作短路方案。

现有证据支持“B580 可以运行官方 FSR 组件”，不支持“本项目接近可玩内置 FG”。候选通过率 81.47% 只是内部闸门统计，不能量化项目完成度。

## 比原先更难还是更易

底层接通、Windows 构建、DXVK interop 与 B580 SDK 执行，比完整交付目标更早完成。它们是可复用的进展。

真实输入的可信度、动态几何、显示调度和 GPU 预算仍是核心未通过项。静态墙体也有明显变形，意味着不能仅把剩余问题归为骨骼运动或透明特效的收尾。当前证据要求上调交付风险，不能根据原型接通很快下调整体难度。

之前“3～6 个月”没有建立在已验证关键路径、真实输入契约和独立硬件性能基线之上，应撤回它作为交付排期的意义。既不能承诺该区间能完成，也没有依据把难度说成 LDB 的固定几十倍。内置路线应按高风险图形逆向／集成研发管理；成品外部路线则主要是兼容性与效果验证。

第一阶段文档已经识别了输入、队列和呈现风险，后续为了快速跑通，采用 Host shader 观测、估算运动、自定义调度与保护合成。它们适合暴露问题，但没有消除最初的工程工作。此前连续改良保护规则的优先级应让位于输入真值、SDK 原始输出和时间预算验证。

## 60→120 的时间预算暴露了架构问题

60 个真实帧的周期为 16.67 ms，120 Hz 的显示间隔为 8.33 ms。并非简单要求某个 FG pass 必须低于 8.33 ms，而是要在持续渲染与插帧负载下保持每 16.67 ms 一个真实帧，并由调度器均匀输出两个显示帧。CPU/GPU 异步有助于流水化，但不能消除 GPU 工作量。

最新 B580 1920×1200 会话，排除截图帧后的生成阶段统计：

| 指标 | 中位数 | 范围解释 |
| --- | ---: | --- |
| 旧自研预检／候选生成 GPU 时间 | 20.63 ms | 不是官方 SDK 内核时间 |
| Host Present 包装工作 | 31.81 ms | 包含阶段工作与同步等待 |
| Fence 等待 | 30.38 ms | 不是纯算法执行时间 |
| 源帧到达间隔 | 41.23 ms | 不是显示器 FPS 或延迟测量 |

当前旧预检一个阶段已超过 16.67 ms，而且运行路径多次同步等待 GPU。即使先修复画质，当前测量下的串行路径也无法自然兑现 60→120。这不能外推为 B580 无法执行高效 FG，也不能把 31.81 ms 全算到官方 FSR 头上；SDK 的独立 GPU 成本尚未测出，几个中位数也不能直接相减当作它的耗时。

当前链路实际叠加了旧候选生成／图像匹配、FSR 输入转换中的另一轮局部图像匹配、官方 Optical Flow/FI、自定义区域合成和多次等待。诊断成本已经进入主运行路径。交付路线需要去掉重复估计与验证性阻塞，而非无限优化每一层。

帧间隔变大也会增加图像运动跨度、光流匹配难度。这说明性能架构与重建正确性需要共同约束，不能在“先正确”阶段完全忽略目标输入频率。

## 路线比较

| 路线 | 对当前目标的评价 | 主要代价／限制 |
| --- | --- | --- |
| 原生稳定 120/144 | 在目标场景确实能做到时优先 | 未来高负载光追不一定仍有此余量 |
| 成品外部画面 FG，如 Lossless Scaling/LSFG | 若只求可用 60→120，优先验证 | 商业产品、捕获模式约束、GPU 余量、HUD／遮挡伪影及额外延迟；B580 实际效果未验证 |
| 精简内置 Vulkan FSR | 若必须自有内置实现则保留，但按有门槛研发推进 | 输入逆向、动态几何、资源调度和呈现仍需工程工作 |
| 改为当前 XeSS-FG SDK | 不是当前 Vulkan 项目的直接捷径 | 官方路线要求 DirectX 12、XeLL、深度／运动／矩阵等；需要额外 API 桥接或后端变更 |
| OptiScaler／现成 FG 注入 | 不能直接补齐 L4D2 的 D3D9/DXVK 输入 | OptiFG 文档标为实验性且 DX12-only，通常还依赖已有受支持超分输入 |
| 整套 l4d2-rtx/Remix 移植 | 不适合作为只求 60→120 的快捷方案 | 场景重建和兼容层改造大，应按光追目标单独评价 |

外部画面插帧绕开了引擎深度、相机及骨骼历史的采集，但仍有光流误判、界面与延迟问题。推荐的是先用成品验证目标是否满足，不是承诺其画质无伪影，也不是建议再从零开发另一套纯图像算法。本环境没有实际运行 Windows/B580 的外部方案；Steam 商店正文受网络策略限制，因此不对当前价格、版本和具体兼容性作核验声明。

当前 Intel 官方 XeSS 3 FG 指南明确要求 DirectX 12 和 XeLL，并继续要求资源标记、深度和运动数据。B580 满足硬件家族条件，不等于能把现有 Vulkan 资源直接传给它。OptiScaler 的 Vulkan 超分支持也不等于 Vulkan FG 支持。

60→120 改善的是呈现流畅度，不会提供原生 120 的输入与仿真响应。未来若光追本身已占满 GPU、只能维持 60，开启 FG 还需计算预算，未必能继续维持 60 个真实帧，不能把关闭 FG 的 60 当作开启后的保证。

## 如果坚持内置路线，使用门槛而非连续盲修

1. **独立 B580 基线**：在目标分辨率，用已知正确的输入分别验证官方原始输出与 GPU 耗时，排除旧自研预检、补丁合成和截图耗时。若基本工作负载没有足够余量，先变更配置、算法或目标分辨率。
2. **真实静态场景输入**：验证同一真实帧的深度、引擎相机、运动方向／尺度与资源时序。优先取得可信引擎元数据，不继续把反复调整的图像匹配当作真值。静态场景未通过前，不用人物保护掩盖它。
3. **精简运行与呈现**：保留 interop、日志和构建，移除重复全屏搜索；设计资源历史、异步依赖、限帧和原帧／生成帧输出节奏。可研究官方 pacing proxy 与 DXVK 的完整适配，或经过明确验收的自定义调度，不能只增加 Present 调用。
4. **动态场景验收**：再解决模型／骨骼、安装式武器、透明特效和 HUD；每轮采集同时保存同帧输入、SDK 原始输出与最终输出，明确本轮要否证的假设。

这不是新的完成日期承诺。任一前置门槛长期无法满足，就暂停内置路线、改变实现边界或转成品方案；不把反复上传截图本身视为收敛。
