# v5：一次采集完成照明对照、材质样本与正确法线预览

v4 的实际地图数据已证明受限世界几何可以进入 RT 输出，后续不再重复独立三角形或纯观察验收。v5 解决的是下一步诊断的可比性：同一次 F9、同一位置、同一运行时，保留原灯光与两种有明确参数的光源对照，并记录实际材质纹理状态。它尚未宣称修好了完整地图照明、HUD 或武器。

## 为什么先区分照明与材质

固定运行时 `b73eb23053aa50d3787b0c6c8b4b8ae49962880e` 的 `rtx_light_manager.h` 定义球形 fallback 为类型 1；`rtx_light_manager.cpp` 将它放在相机位置加 offset。v4 半径 5、辐射度 30 的球灯不是环境照明，远处物体接收到的光随几何关系显著减小。这个机制能解释偏暗的一部分，但没有证明它是唯一原因。

同一版本的 `d3d9_rtx.cpp` 在 fixed-function 转换时，从原 D3D9 的纹理阶段、UV 索引、纹理因子、sRGB sampler 等状态提取旧材质。我们此前只转换了世界顶点与矩阵，没有重新配置这些状态。下一包读取有界样本来确认实际输入，不先把所有材质强制改成同一种颜色或放宽白名单。

自动曝光与局部 tone mapping 使用本运行时默认参数并显式记录，三段不变。自动曝光可能抵消一部分亮度差异，不能按球灯辐射度比值期待最终颜色恰好变亮 100 倍。阶段请求成功也不等于已经确认后端生效或曝光收敛，需结合实际图像、深度/法线与日志判断。

## 同一次 F9 的安排

| Present | 内容 | 读回 |
| --- | --- | --- |
| 1–30 | 原有 Remix 光栅控制段 | 30：颜色、深度、法线 |
| 31–120 | 原球灯：类型 1，半径 5，辐射度 30 | 120：三类输出 |
| 121–180 | 保持球灯和半径，只把辐射度设为 3000 | 180：三类输出 |
| 181–240 | 类型 0 定向灯，方向 `(0,0,-1)`，辐射度 3 | 240：三类输出 |

每个阶段先读回旧结果，再请求下一组参数；固定运行时延后到帧边界应用。设置失败会标记失败、请求关闭 RT 并停止转换，不能把部分设置成功标成完整阶段。定向灯用于对照室外照明；室内被几何遮挡时仍可能较暗，不是最终地图光源方案。

用户只需在地图中面向同时含地面与墙壁的位置，按一次 F9，保持镜头静止直到提示结束，再正常退出并上传一个 ZIP。无需切换开关或分三组运行。每次读回记录最后一个转换世界 Draw 的 view/projection，分析器检查阶段末端矩阵是否接近；这只能检查端点，不能证明期间场景或相机完全静止。

每段最多对 64 个转换材质身份读取一次恢复后的原始 public D3D9 状态：8 个纹理阶段的操作、参数、UV 索引、纹理变换开关与结果目标，纹理类型/尺寸/格式，sRGB 开关及 pixel shader 绑定情况，并记录 TEXTUREFACTOR、固定功能光照/顶点颜色来源、环境色、fog 和 sRGB 写入开关。getter 返回的引用立即 Release，没有新增状态修改。这是有限样本，不覆盖每次纹理变更、纹理内容或完整 PBR。

仍使用原 240 Present / 128 MiB trace 和 192 MiB 结果预算。新增一组读回约 12.3 MB，原始读回合计 49,152,000 字节，不扩大逐 Draw 二进制包体；本次 v4 实际数据对应的总量估算仍在结果预算内。复杂场景仍可能触发原有预算，届时按 incomplete 保留证据。

## 分析修正

法线来自固定 primary GBuffer 的 R32_UINT。按 `packing_helpers.h` 的 unsigned-offset Snorm2x16、除数 65534 和 signed-octahedral 公式解码；不能把 RGBA32F 中承载位模式的 NaN 当作 GPU 数值错误，也不能把 packed word 0 一律当作空值，它可表示 -Z。只有同帧深度 `0<z/w<1` 的像素进入法线预览，65535 分量作为无效编码报告。

深度预览显示投影深度对比，明确不是线性距离。颜色保留原 clamp 映射，不加伽马或提亮；同时记录原始 RGB 的亮度统计。新版重析 v4 实际数据，120/240 帧解码预览与此前独立生成的 PNG 字节完全一致，有效覆盖分别为 83.5578125% / 80.048828125%，有效深度处无非法法线编码。这属于旧数据回归，不是 v5 新实机验证。

## HUD / 武器路径评估

[现有 Draw 路由复核](../../research/rt-world-v5-shader-routing-review.json) 来自正确的 v4 ZIP，无需用户补采。实际后处理为每帧一次的 `Neko_Engine_Post`；参考兼容 mod `1fc8ded63a8491e9c1972eb2940d6cebbc20ad9e` 的 `model_render.cpp` HUD 分支匹配 `shader_name.starts_with("Engine_")`，不会匹配此名称。参考分支还重建屏幕淡入淡出 quad 并读取 Source fade color，并非只放行一个 shader 就能合成所有 HUD。

实际 `UnlitGeneric` 既有 backbuffer 上禁用深度的候选，也有 HDR/场景与近深度范围绘制；`VertexLitGeneric` 同样横跨世界和近范围对象。名称不能单独作为 UI 或武器标签。后续应在已验证的 Draw/状态作用域内适配真实后处理注入点及屏幕绘制，对武器另验证压缩顶点、蒙皮与相机深度范围。v5 保留严格世界白名单，不迁入参考 mod 的全局 prim context，也不写 Source 线程 CVar。
