# 跳过插帧、优先研究光追的路线评估

日期：2026-10-15（用户时区 America/Los_Angeles）。本轮是路线审视，没有新增光追实现或 B580 实测。

后续约束更新：用户要求大量复用 l4d2-rtx，同时取消其强制关闭 Source 部分渲染线程的限制。执行顺序以 [多线程 RT 实施计划](multithreaded-rt-implementation-plan.md) 为准，先建立有序接入和观察模式，再将 B580 兼容性、材质队列与最小静态 RT 合并测试；不把默认单线程配置作为正式目标。

## 结论

路线优先级会改变。FG 不是光追的前置条件。如果真正希望的是光追画面，可以暂停内置 FG，把 l4d2-rtx 与匹配 Remix runtime 的 B580 兼容性／性能基线放到第一位。此时复用成熟 RT 项目具有直接价值，而不是仅为了 FG 引入整套场景重建。

但不能推导为完整光追比 FG 更容易。静态、单效果硬件光追可以形成边界清楚的早期成果；全游戏动态、反射／GI／路径追踪则需要比当前 FG 实验更完整的场景、材质与光照数据。

用户目标仍应以高压场景保持约 60 个真实帧为约束，之后能否用外部 FG 补到 120 是独立验收。不能把现有光栅高压 60～80 FPS 当成启用 RT 后的保证。

## 当前资源能复用什么

可复用 LDB、x64 Host、DXVK interop、资源标识、日志和构建体系，以及已找到的相机／视模／HUD 观测位置。当前颜色和深度不等于完整场景：光追还需要顶点与索引、实例变换、蒙皮／形变后的几何、法线／UV、材质与透明裁剪、光源和稳定的资源生命周期。

射线会命中屏幕外和被遮挡的物体，最终画面与深度只有可见表面，不能据此恢复完整世界。RT 第一阶段不应继续采用从最终图像猜全部场景的路线。碰撞网格也不能自动替代渲染网格及透明材质。

当前帧 RT 可先不使用完整时间历史，因此单个静态阴影／遮挡实验比通用 FG 更容易作几何真值验证。但后续降噪、动态阴影、GI 与反射仍会引入时间历史和运动一致性问题。

## 三条主要路线

| 路线 | 价值 | 主要成本／风险 |
| --- | --- | --- |
| 直接验证 l4d2-rtx + 匹配 Remix | 最快检验已有成果是否能用于本机，场景提取、渲染和降噪可大量复用 | B580 兼容性、版本/API 对齐、线程／蒙皮代价和高压性能未验证 |
| 保留原光栅，增加限定硬件 RT 效果 | 更容易限制预算，适合先研究静态世界 AO／可见性或一盏灯的阴影 | 仍需真实几何和可靠相机，动态遮挡／透明／材质逐步接入，不能保证最后一定维持 60 |
| 从零实现完整 Vulkan 光追渲染器 | 控制力最大 | 场景提取、蒙皮、PBR、光照、反射、GI、降噪及生命周期工作最大，暂不建议作起点 |

屏幕空间 SSR／SSGI 可以作为画面效果选项，但无法替代完整场景硬件光追，不把它当成同一验收目标。

## B580 与 Remix：不能凭名称判定，也不能直接承诺兼容

本次查看的当前 Remix `3bde35c3268fe16f4d8075acc7d27340abeb4277`，核心要求包含 `VK_KHR_acceleration_structure`、`VK_KHR_ray_query`、`VK_KHR_ray_tracing_pipeline` 和 buffer device address。所查 NV interop 与 invocation reorder 扩展标为 Optional；context 中有不支持 DLSS 时转到 TAAU、禁用不支持 DLFG 的路径。

这些源码支持研究非 DLSS 路径，不能据此认定整个 runtime 已在 B580 正确运行。仍须检查具体驱动的扩展／feature、设备配置、降噪／重建路径和实际错误。B580 具有硬件光追能力，也不等于某个 Remix 包及 L4D2 mod 已兼容。当前没有本机 RT feature probe 或现成 L4D2 RTX 实测。

本次研究的新 Remix 与项目 Bridge 基线、旧参考版本不同；应使用互相匹配的包和 API，不假设替换一个 DLL 即可。未验证的非 NVIDIA 路径不应被写成现成支持承诺。

## 单线程问题仍须正视

固定 l4d2-rtx `1fc8ded63a8491e9c1972eb2940d6cebbc20ad9e` 的兼容设置包含：

- `mat_queue_mode = 0`
- `r_threaded_particles = 0`
- `r_threadeddetailprops = 0`
- `mat_softwareskin = 1`

它们关闭部分渲染并发、使用 CPU 蒙皮，不表示 AI、音频及整个游戏全都单线程。对于原生高压已经 60～80 FPS 的场景，这些 CPU 成本可能非常关键。

硬件光追 API 本身不要求上述游戏设置。若只参考其 Hook、相机与几何提取，保留原线程模型在设计上可研究，但仍须验证并发采集与渲染语义；不能把取消这些兼容设置当作无成本修改。

## 推荐验证顺序

1. **先做现成路线基线**：B580 上验证硬件 feature 和匹配的 l4d2-rtx／Remix 路径，不启用 FG，记录正确画面、错误、CPU/GPU 时间、超分／降噪回退路径。若已有方案可用，就优先评估直接复用，避免先写另一套渲染器。
2. **用高压场景决定取舍**：检验 RT 开启后是否还存在真实 60 的余量，区分 CPU 场景处理与 GPU 光追开销。完整路径不适用时，先决定是否接受限定效果，而非自动展开漫长移植。
3. **若做自有轻量路线，先验证几何**：可靠引擎相机、静态不透明世界、BLAS/TLAS、射线命中调试图。再增加一种明确效果。阴影应正确作用于所选光源／光照分量，不盲目叠乘包含烘焙光照的最终颜色。
4. **最后扩展动态与材质**：感染者／骨骼、安装式武器、alpha test、透明、水与粒子，以及降噪和 PBR。每轮一次收集几何调试、输入与原始 RT 输出、合成和 CPU/GPU 时间，不继续用单个“成功调用次数”验收。

如果主目标为完整路径追踪画面，直接评估已有成熟路线应优先；如果主目标为保留原玩法并维持高压 60，有限硬件 RT 效果更适合控制研究范围。两者不能使用同一个难度和工期承诺。

可信几何、相机与实例身份将来可以帮助 FG，但 RT 当前帧能命中正确物体，不会自动证明前帧变形、运动矢量、HUD-less 合成或 120 Hz 调度正确。
