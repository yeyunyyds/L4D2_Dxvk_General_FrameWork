# 多线程 RT 统一测试与采集规格

状态：完整用户套件的接口和验收规格，配合 [实施计划](multithreaded-rt-implementation-plan.md)。[开发协调器与协议观察](rt-foundation.md) 已实现；游戏安装／启动／回放尚待接入。旧 FG 包尚无本页的启动器、热键语义或输出文件。

## 一个入口、一次综合操作、一个结果 ZIP

拟提供 `start_rt_suite.cmd`，调用测试协调器。它完成文件校验、探测、分 profile 启动、游戏内提示、自动回放、结果校验与打包；用户不用打开 CMD 设置环境变量或创建 `capture.trigger`。

用户流程设计为：

1. 按该版说明安装完整匹配包，双击总入口。安装／恢复工具记录改动和备份；如果初次启动确需退出 Steam，只在最初处理一次。
2. 进入指定本地官方地图，在出现“RT 综合测试已就绪”后按一次 F8 开始，按提示完成约两分钟的观察、转头／移动、射击／换弹和战斗。高压段由实体数量和耗时标记确认；允许继续录制直到必需内容覆盖。
3. 协调器停止录制并顺序回放适用 profile，分别做图像诊断与性能测量；需要设备／backend 重建时自动重新启动测试进程。测试结束或进程退出后输出一个结果 ZIP，上传它即可。

F8 在新 RT 套件中只负责开始／结束录制，不启停渲染线程，不暂停游戏，不承担 RT A/B 切换；录制达到有效时长且覆盖齐全时可以自动结束。F9 不参与。旧 FG 的热键处理与生成逻辑在 RT profile 中禁用，避免两处同时响应。热键只在目标游戏前台接受。

demo／自动地图加载必须先经过本版本验证，不把这段设计描述为当前可用命令。回放失败时保留同一会话的分段手动流程和未完成标签；无须拆成多个上传。任一 profile 崩溃后停止该 profile，保留失败包，不无限重启。对仍能安全执行的独立对照可继续，但不得自动重复故障路径。

## Profile 与启动隔离

| ID | 模式 | Backend 与 Hook | 用途 |
| --- | --- | --- | --- |
| R0 | `raster_control` | 固定的 LDB／普通 DXVK，FG 关闭，新 RT Hook 不改绘制与画面 CVar | 原有渲染和高压预算对照 |
| R1 | `hook_observer` | 与 R0 相同 backend，新的队列／线程观察 Hook；不做固定功能转换和 RT 状态修改 | 检查 Hook 本身的侵入性、队列身份和开销 |
| R2 | `rt_mt_static` | 匹配的 Remix 与静态世界转换，材质队列保持启用 | 批次 A 的实际 RT、几何／相机和并发验证；动态未覆盖单列 |
| R3 | `rt_mt_full` | 与候选版匹配的 Remix、动态／材质处理及所要求的并行路径 | 批次 B 的完整质量、生命周期和性能 |

批次 A 执行自动 runtime 探测和 R0／R1／R2；批次 B 执行当前包版本的 R0／R1／R3。没有单线程的正式测试 profile。相同源 demo 的多次回放由协调器安排，不需要用户按 profile 重新做动作。

profile 固定在进程启动时读取。采用可识别 session／run 的本地启动清单及握手，避免反复依赖 Steam 环境变量继承；具体 loader 机制在 P0 确认。每次启动验证实际载入 DLL 路径、架构、SHA、API 及配置，不能只记录“打算载入”的文件。

同一进程不热换 DXVK／Remix，不运行中强改 `mat_queue_mode`。协调器只管理本次创建并握手确认的进程，等待退出与文件释放后再切换 profile；不结束其他 Steam／游戏会话。需要重新安装文件的布局必须在启动前完成并验证，结束时恢复本次临时设置。

R0／R1 使用相同分辨率、地图、demo、fps cap 和画面配置。R2／R3 中 RT 需要的光照／材质设置差异逐项记录；RT 总成本可以和 R0 比较，但不能把不同画质组合的差值冒充纯 Hook 或某个 RT pass 的成本。

## 自动诊断与性能分段

| 区间 | 自动动作 | 数据与限制 |
| --- | --- | --- |
| 启动 | 版本／文件／功能／API 探测；建立进程与会话关联 | required feature 缺失也打包；扩展存在与实际创建、射线执行分开 |
| 预热 | 等主视图、有效地图、焦点、连续帧与关键资源就绪；记录 shader／AS 冷启动 | 不只等待固定秒数。预热至少 15 秒并检查完成条件，超时标记失败／未完成 |
| 质量诊断 | 按相机运动、动态对象、粒子／透明、薄边缘和错误选择短 burst | 数据都带同一帧／视图／draw 身份；截图读回停顿单独计数 |
| 性能 | 同内容正常速度再回放，默认每个必需性能段至少 60 秒 | 禁用图像回读、逐 Draw Get 状态及同步校验；批量事件和 GPU 时间戳异步读取 |
| 生命周期 | 录入实际失焦／重新聚焦、换图、退出；在可控配置下尝试设备／尺寸恢复 | 必须观察到相应事件才计通过；未产生 Reset 不能宣称覆盖 Reset |
| 收尾 | 校验完整性、保存摘要、压缩所有子运行和恢复记录 | 正常退出和崩溃部分包都保留；每个必需场景给出覆盖状态 |

选择 burst 时以主视图有效性、场景绘制和焦点为条件。切回窗口产生的几帧静止或交互不会被自动当成“纯静止样本”；相机运动和事件才是分类依据。只剩菜单／最终 backbuffer 的区间不冒充世界采集。

质量诊断与性能是同一总入口下的两个执行区间，必要时是两次回放。一个 ZIP 中同时保存，但报告分开；质量回读耗时不能污染生产性能结论。

默认全会话最多 8 个 burst，每组连续 4 个真实帧；最多 2 组优先保存原生分辨率关键数据，其余用明确记录采样映射的预览。原生关键组优先覆盖静态边缘与动态／武器，不再仅凭低分辨率预览验收细节。

默认未压缩预算为 1 GiB：图像 512 MiB、所选几何／骨骼 256 MiB、详细 trace 128 MiB、其他日志 64 MiB。只保存代表性 mesh／更新范围和一次去重资源，不能每帧导出完整地图。达到预算后停止相应详细输出并记录缺失项；低开销计数、退出信息和 summary 继续。若必要证据没有保存，该项不验收为通过。

## 结果目录与字段

拟输出 `rt-results/session-<id>.zip`，包含以下结构。下列路径和 schema 为实现目标，不代表现有分析器已能读取。

```text
session-manifest.json
summary.json
versions.json
capabilities.json
scene-coverage.json
restore-report.json
replay/                         # 同一次录制；地图、demo SHA、tick 范围
runs/<runId>/
  run-manifest.json             # profile、PID、实际模块、配置及状态
  client-events.jsonl
  host-events.jsonl
  frame-metrics.jsonl
  thread-trace.bin              # 有界详细事件，非整场无限 per-draw 文本
  resource-manifest.json
  captures/<burstId>/...
  logs/...
  crash/...                    # 仅本次进程失败时的可用诊断
```

`session-manifest` 声明计划运行列表、schema、包版本、开始／结束、终止原因和完整性。`summary` 对版本、RT、顺序、画面、覆盖、生命周期、性能分别给出 `pass / fail / unrun / not_exercised / unavailable / incomplete`，不提供一个误导性的“总成功率”。

| 类别 | 必需字段／证据 |
| --- | --- |
| 版本与环境 | Windows、CPU／核心数、内存、GPU／驱动、实际适配器、游戏各模块 build／SHA、插件／Bridge／runtime 实际加载 SHA、配置／分辨率／内部比例／fps cap；原值、请求值与实际 CVar |
| 能力与实际执行 | required／optional feature、设备创建结果、所选扩展／重建／降噪路径、API 握手、最小 RT 场景输出和错误；通用 Vulkan 探测不能替代 Remix 执行 |
| 帧与视图 | session／run／PID、device／map generation、真实主视图帧、view kind／ordinal、draw／command sequence、资源 ID／版本及对应 Present |
| 时钟 | 每进程 QPC 与频率，入队／消费相关 ID；GPU 查询单位、有效位与结果可用性。跨时钟域先校准或只比较各自持续时间，不能直接相减 |
| 线程与队列 | Hook／线程 ID、生产／执行阶段、任务开始／结束、入队与消费、队列深度、忙碌时间、等待原因／耗时、重入和状态作用域闭合；轻量计数与详细 trace 区分 |
| 相机与几何 | 实际引擎相机／投影／near／far／viewport、mesh／instance／material ID、顶点／索引格式与范围、实例／骨骼变换、动态 buffer 更新版本；必要的命中位置和对象 ID |
| 材质与画面 | alpha／透明／粒子／水／decal／HUD／武器分类，原始 RT 输出、选定命中／深度／法线／实例调试图与最终合成；标明主视图和采样映射 |
| 性能 | CPU 准备／队列／消费／等待分段，AS 构建／更新、可测的 RT／降噪／合成 GPU 时间与总 GPU 时间，真实帧与 Present 间隔、16.67 ms 超限比例、显存／内存、冷启动事件 |
| 生命周期与失败 | 地图／设备／资源失效、待完成任务和释放确认；进程退出码、最后心跳、Bridge／Remix 日志、在自身进程可用的 crash 信息／minidump、恢复结果 |

画面与几何输出跟随实际实现能力：缺少原始 RT 或某个 GPU pass 时长时明确记录 `unavailable`，不使用最终合成或 CPU 等待冒充。完整动态质量验收需要至少一组原生连续帧和同帧几何／实例证据。

## 一次录制要覆盖的内容

游戏内用简短提示引导，事件自动打标签，不要求用户手写文件名前缀：

- 安静主场景中的静止、缓慢转头和移动；包含近处几何、远处边缘、天空。
- 动态模型、武器射击／换弹和 HUD；条件允许时包含安装式武器，避免只覆盖第一人称武器。
- 战斗与足够持续的高压；统计感染者／幸存者、draw、粒子和实际 CPU/GPU 开销，不能凭“在地图里”判断已覆盖尸潮。
- 本地图可见的 alpha test／透明／水／粒子／绳索／detail。地图没有某类对象时记为未覆盖，在同一套件追加对应地图子运行，不宣称全覆盖。
- 结束时的失焦恢复和一次地图／资源重建。尺寸变化／Reset 如果不具备可靠自动化，保留一次游戏内提示操作并记事件；不会要求通过切出 CMD 触发。

demo 是复用测试内容的手段。每次回放核对地图／demo SHA、tick／视图／实体标记、播放速率和有效区间；不支持或不等价的部分只做独立检查。高压回放需要保持正常游戏速率，不能提前渲染完 demo 后从 `timedemo` 的 FPS 推导锁 60 表现。

## 云端先做的验证

发给用户前，至少完成以下与改动相关的检查：

- 真实 x86／x64 Release 构建，PE 架构、依赖、协议／API、加载路径及 package SHA 检查；测试包能够报告缺 DLL 和旧协议。
- 多帧 producer／consumer 重叠、嵌套 view、未知命令、越界长度、资源 ID 重用、更新／销毁／Reset、背压与消费延迟的协议执行用例。
- 作用域状态在正常和异常路径恢复；动态 buffer 版本与数据所有权的用例，避免只验证结构体能序列化。
- 协调器使用可控子进程验证顺序启动、正常／异常退出、超时、残缺数据、预算耗尽和仅一次压缩输出；演练恢复本次改动，不覆盖其他文件。
- 对已有软件设备能执行的 D3D9／Hook／图像采集路径做实际冒烟；RT 硬件与真实游戏线程部分明确留给 B580，不用零测试或编译成功代替。

基础部分的已执行检查见 [验证记录](../../research/rt-foundation-validation.json)；剩余检查不因协议或编译通过而标为已完成。

## 补测规则

分析器先检查包、版本、覆盖和数据关联，再检查质量与性能。只有能说明“本次哪项证据缺失／哪条改动需要重新验证”才安排补测；补测包仍携带该路径的输入、原始输出、最终画面、时序和性能，不再分多轮补同一问题的字段。

综合 A 的已通过结论保留对应版本身份。B 更新了协议、队列或 runtime 时，同一个 B 包自动重跑相关 A 门槛；不沿用旧版本结果冒充回归通过。
