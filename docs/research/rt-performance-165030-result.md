# RT Performance v31 165030 结果与 v32 隔离验证

v31的30帧门禁成功。GPU蒙皮上限4的阶段完成60帧，用时16,011.0 ms，约3.75 FPS；240次GPU蒙皮提交只创建6个持久网格并复用234次。该阶段GPU 3D Engine平均13.1%、最高21.2%。第90帧仍有694个模型提交，新建约95.96 MB几何；累计创建39,414个网格、销毁38,073个。性能测试同时运行了持久GPU蒙皮和大规模逐姿态CPU网格重建，没有隔离GPU路径。

进入上限64的阶段后只留下约6帧运行期输出。`remix-dxvk.log`在16:58:46.276记录`VK_ERROR_DEVICE_LOST`，随后等待空闲与命令提交也失败。Bridge之后等待已经失效的Host命令60秒并中止；游戏音频仍正常，说明Source游戏逻辑继续运行，而x64渲染设备已丢失。退出时`necola.dll`访问异常发生在设备丢失之后，属于清理阶段后果，不能解释最初冻结。

进一步检查Remix历史实现后，不能把故障归因于主命令列表与独立蒙皮列表的表面调用顺序。主列表先提交已有几何上传，GPU蒙皮随后写入，BLAS工作在新的主列表中记录；直接颠倒可能让蒙皮读取尚未提交的绑定姿态数据。因此撤销顺序变更。可确认的小问题是`m_skinningCommands`在真实刷新后没有清零，后续会反复刷新空列表；v32只修正该计数。

v32的主要变化是隔离工作负载。性能模式只提交已审计的持久GPU蒙皮网格；不适合GPU蒙皮、包含形变或超过当前档位的模型不再建立CPU姿态网格；达到当帧档位上限后，剩余模型还会在读取几何前直接省略。一次F9运行120帧，16、32、64、128各30帧。日志要求每个显式模型提交都带GPU蒙皮，并报告持久网格创建／复用、Host各阶段耗时、帧率和GPU Engine数据。这个版本先判断纯GPU路径能否稳定越过64／128档；不用于评价画面完整性。
