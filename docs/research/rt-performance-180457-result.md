# RT Performance v33 180457 结果与 v34 供给优化

上传包匹配 v33 提交 `2f1f8df56c584c66d688d70cb7fd92878e9953e5`。纯 GPU 蒙皮预览完成四档共 120 帧、4,800 次蒙皮提交，没有 `VK_ERROR_DEVICE_LOST`、API fence 失败或恢复遗留。四个档位的最后一帧分别有 16、32、48、64 个蒙皮提交，唯一 Mesh 数与提交数完全相等，重复姿态 Mesh 全为 0。v33 的“每个同时姿态使用独立持久句柄”修正已经通过本轮稳定性验证。

采集器把第三、第四时间窗误标为 `gpu_ramp_64` 和 `gpu_ramp_128`，而 Mesh 证据与实际上限正确地是 48 和 64。这使自动分析错误报告缺少 48 档；不是运行端跳过了档位。v34 已把时间窗名称修正为 16、32、48、64。

| 每帧 GPU 蒙皮 | 30 帧 FPS | Host 模型处理/帧 | SHA-256/帧 | Host 3D 平均 | Host 3D 最高 |
|---:|---:|---:|---:|---:|---:|
| 16 | 8.91 | 4.17 ms | 1.03 ms | 10.54% | 22.30% |
| 32 | 14.04 | 8.97 ms | 3.16 ms | 27.75% | 28.04% |
| 48 | 13.50 | 12.97 ms | 4.94 ms | 42.51% | 48.65% |
| 64 | 13.54 | 15.96 ms | 6.30 ms | 50.69% | 52.02% |

16 档包含一次 1,308 ms 的首用 Present 停顿，不能用来与后三档直接排序。GPU 3D 采样随蒙皮上限单调增长，证明计算确实在 B580 上执行；Task Manager 的整卡数字与这个按 Host PID 过滤的 3D Engine 计数器不是同一口径。64 档仍只有约 13.5 FPS，且 CPU 供给开销随提交数线性增长。其中每帧约 6.30 ms 是相同网格的重复 SHA-256 计算及哈希对象创建。

v34 保留完整 SHA-256 网格身份和 v33 姿态槽，改为每个准备线程复用一个 CNG 哈希句柄，旧 CNG 不支持时保留独立句柄回退。这一步不改变几何身份、Remix 命令顺序或线程所有权，用同一次 120 帧采集直接比较 Host 哈希时间。

游戏在 RT 恢复和 Bridge 正常清理后，于退出过程在 `necola.dll+0x1447fc` 发生了一次 `0xc0000005` 执行异常。异常发生时没有活动 Bridge 命令，Host 已报告清理成功；因此它不推翻本轮 GPU 稳定性证据，但退出状态仍应保留为异常，不把外部模块崩溃改写为正常退出。
